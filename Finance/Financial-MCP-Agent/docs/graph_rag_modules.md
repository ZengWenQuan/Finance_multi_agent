# Graph RAG 模块详解

## 1. 什么是 Graph RAG

Graph RAG 是在传统 RAG 的基础上，引入 **图结构知识组织方式** 的检索增强生成系统。

传统 RAG 的核心思路通常是：

1. 把文档切块
2. 给文本块做向量化
3. 用户提问时召回相似文本块
4. 把召回结果交给 LLM 生成回答

Graph RAG 则进一步做了两件事：

1. 不只保存文本块，还会抽取 **实体、关系、属性**
2. 把这些信息组织成图，支持 **结构化检索、多跳扩展、社区发现、社区摘要**

所以它更适合回答这类问题：

- 某家公司有哪些主要风险
- 某个行业上下游关系如何
- 某家公司和同行、产业链、事件之间有什么关联
- 哪些信息分散在多个文档位置，但本质属于同一个主题

---

## 2. 一个完整 Graph RAG 通常包含哪些模块

一个较完整的 Graph RAG 系统，通常可以拆成下面这些模块：

1. 文档接入模块
2. 文本预处理模块
3. 实体抽取模块
4. 关系抽取模块
5. 图构建模块
6. 图存储模块
7. 社区发现模块
8. 社区摘要模块
9. 向量索引模块
10. 查询理解模块
11. 图检索模块
12. 向量检索模块
13. 上下文重构模块
14. 回答生成模块
15. 评估与反馈模块

下面逐个说明。

## 3. 各模块的功能

## 3.1 文档接入模块

### 作用

负责把原始数据送入 Graph RAG 系统。

### 输入

- PDF
- 网页
- Markdown
- 新闻
- 财报
- 数据表
- 数据库记录

### 输出

- 统一格式的原始文档对象

### 它解决的问题

不同来源的数据格式差异很大。这个模块负责做“入口标准化”，让后面的流程不需要关心数据来自哪里。

### 典型职责

- 读取文件或接口数据
- 保存原始文档元信息
- 分配文档 ID
- 记录来源、时间、标签、业务域

---

## 3.2 文本预处理模块

### 作用

把原始文档整理成适合抽取和检索的形式。

### 输入

- 原始文档

### 输出

- 清洗后的文本
- 文档分块
- 标准化后的段落结构

### 它解决的问题

原始文档里可能有：

- 噪声字符
- 重复内容
- 表格残缺
- 页眉页脚
- 非结构化段落

如果不先预处理，后面的实体抽取和关系抽取质量会明显下降。

### 典型职责

- 文本清洗
- 分段
- 标题识别
- Chunk 切分
- 时间、数字、单位格式标准化

---

## 3.3 实体抽取模块

### 作用

从文本中识别重要实体。

### 输入

- 预处理后的文本块

### 输出

- 实体列表

### 常见实体类型

- 公司
- 股票代码
- 行业
- 产品
- 风险事件
- 财务指标
- 人物
- 地区
- 时间

### 它解决的问题

Graph RAG 里的图，不是凭空生成的，必须先知道“图里有哪些点”。实体抽取模块就是负责找出这些点。

### 典型职责

- 命名实体识别
- 实体类型判断
- 实体标准化
- 别名归一化

例如：

- “贵州茅台”
- “茅台”
- “600519”

可能最终都要映射到一个核心实体。

---

## 3.4 关系抽取模块

### 作用

从文本中识别实体之间的关系。

### 输入

- 文本块
- 抽取出的实体

### 输出

- 三元组或多元关系

例如：

```text
(贵州茅台, 属于行业, 白酒)
(贵州茅台, 存在风险, 原材料价格波动)
(贵州茅台, 发布于, 2024Q1财报)
```

### 它解决的问题

实体只是图里的“点”，关系模块决定“点和点之间怎么连”。

没有关系抽取，图就只是一个实体清单，不是可推理的知识网络。

### 典型职责

- 从句子中抽关系
- 判断关系方向
- 给关系命名
- 提取关系属性

### 关系抽取方式

- 规则/模板
- 传统 NLP 模型
- LLM 抽取
- 混合方法

---

## 3.5 图构建模块

### 作用

把实体和关系正式组织成图结构。

### 输入

- 实体
- 关系
- 元信息

### 输出

- 节点
- 边
- 属性

### 它解决的问题

抽取结果通常是离散的，图构建模块负责把这些离散结果组装成统一图模型。

### 典型职责

- 创建节点
- 创建边
- 设置节点标签
- 设置边类型
- 记录来源文档
- 去重与合并

例如：

- 相同公司实体是否合并
- 相同关系是否复用
- 一个风险是否挂多个来源

---

## 3.6 图存储模块

### 作用

把构建好的图存到可查询的后端里。

### 常见实现

- Neo4j
- NebulaGraph
- JanusGraph
- TigerGraph
- 本地 JSON / 内存图

### 它解决的问题

图不仅要建出来，还要：

- 能增量更新
- 能查询
- 能做图遍历
- 能支撑后续分析

### 典型职责

- 写入节点和关系
- 更新已有实体
- 删除旧版本图数据
- 提供图查询接口

- 可选 `Neo4j`

## 3.7 社区发现模块

### 作用

把整张图切成若干“关系密集的子图社区”。

### 输入

- 完整图

### 输出

- 社区划分结果

### 它解决的问题

大图直接检索会很乱。社区发现可以把关系紧密的一组节点聚在一起，形成更高层的主题单元。

例如一个金融图谱里，可能自动形成这些社区：

- 白酒行业社区
- 新能源车产业链社区
- 某家公司风险社区
- 某一轮财报事件社区

### 常见算法

- Leiden
- Louvain
- Label Propagation
- Connected Components

### 它的价值

- 降低图复杂度
- 支持主题级检索
- 为社区摘要提供输入
- 帮助做全局问题回答

---

## 3.8 社区摘要模块

### 作用

为每个社区生成“高层摘要”。

### 输入

- 某个社区里的节点、边、属性、原始片段

### 输出

- 社区摘要文本

### 它解决的问题

用户很多问题并不是问某个单点实体，而是在问一个主题整体。

例如：

- “总结一下这家公司所有主要风险”
- “概括这个行业当前面临的问题”
- “这个产业链有哪些关键矛盾”

这时候，把整个社区压缩成摘要，比单纯返回几十条边更有用。

### 典型职责

- 汇总社区内关键信息
- 提炼主要实体和主要关系
- 生成适合 LLM 使用的摘要文本
- 可进一步做向量化索引

---

## 3.9 向量索引模块

### 作用

为文本块、实体描述、关系描述、社区摘要建立向量表示。

### 输入

- 文本块
- 实体描述
- 社区摘要

### 输出

- 向量索引

### 它解决的问题

图检索适合结构化关系查找，但用户问题通常先是自然语言。向量索引可以帮助系统先做语义召回，再决定去图里查哪里。

### 常见后端

- FAISS
- Milvus
- Weaviate
- pgvector
- Chroma

### 它的价值

- 语义入口
- 模糊匹配
- 跨表述召回
- 社区摘要检索

---

## 3.10 查询理解模块

### 作用

理解用户问题到底在问什么。

### 输入

- 用户 Query

### 输出

- 查询意图
- 关键实体
- 关键关系
- 查询模式

### 它解决的问题

Graph RAG 不是所有问题都该用同一种检索策略。

例如：

- “茅台有哪些风险” 更像实体属性扩展
- “茅台和五粮液怎么比较” 更像多实体对比
- “白酒产业链有哪些关键风险” 更像社区级或子图级查询

### 典型职责

- 实体识别
- 关系词识别
- 查询分类
- 路由策略选择

---

## 3.11 图检索模块

### 作用

根据查询意图，从图中取出相关节点、边、路径或子图。

### 输入

- 查询意图
- 实体候选
- 图数据库

### 输出

- 子图
- 路径
- 关系集合

### 它解决的问题

真正的 Graph RAG 关键就在这里。它不是只“找相似文本”，而是要从图里找到和问题最相关的结构。

### 常见检索方式

- 一跳邻居查询
- 多跳路径查询
- 特定关系过滤
- 子图扩展
- 社区级查询

你现在项目里的图检索还是轻量版：

- 在 `GraphStore.query_related(...)` 里做关键词匹配和简单 Cypher 查询

## 3.12 向量检索模块

### 作用

除了图检索之外，再从向量库里找相关文本或摘要。

### 输入

- 用户 Query

### 输出

- 相似文本块
- 相似社区摘要
- 相似实体描述

### 它解决的问题

不是所有答案都适合通过图来表达。有些问题需要原始文本证据，这时向量检索是图检索的重要补充。

### 常见用法

- 先向量召回，再图扩展
- 先图找到社区，再取社区摘要向量
- 图检索和向量检索混合召回

---

## 3.13 上下文重构模块

### 作用

把图检索和向量检索拿到的结果，整理成适合 LLM 阅读的上下文。

### 输入

- 子图
- 路径
- 社区摘要
- 文本片段

### 输出

- 结构化 Prompt 上下文

### 它解决的问题

LLM 不能直接“读数据库”或“读图结构对象”，必须把结果转换成文本、列表、路径说明、证据块。

### 典型职责

- 把图路径转成自然语言
- 合并重复信息
- 按优先级排序证据
- 控制上下文长度
- 标注来源和可信度

---

## 3.14 回答生成模块

### 作用

让 LLM 基于重构后的上下文生成最终回答。

### 输入

- 系统提示词
- 用户问题
- 检索上下文

### 输出

- 最终答案

### 它解决的问题

Graph RAG 的目标不是展示图，而是给用户一个可理解、可解释、尽量准确的答案。

### 典型职责

- 综合多个证据源
- 做归纳总结
- 保留证据链
- 明确不确定性

---

## 3.15 评估与反馈模块

### 作用

评估 Graph RAG 的效果，并反向优化各模块。

### 常见评估维度

- 实体抽取准确率
- 关系抽取准确率
- 社区划分质量
- 检索召回率
- 回答正确率
- 幻觉率

### 它解决的问题

Graph RAG 很复杂，任何一层出问题，最后答案都会变差。必须有评估模块帮助定位瓶颈。

### 典型职责

- 构建测试集
- 做离线评估
- 对比不同检索策略
- 回放失败案例

---

## 4. 这些模块如何协作

一个标准 Graph RAG 系统，通常分成 **离线构建阶段** 和 **在线查询阶段** 两条链路。

---

## 4.1 离线构建阶段

这一阶段主要负责“把知识准备好”。

协作顺序通常是：

1. 文档接入模块读取原始资料
2. 文本预处理模块做清洗、切块、标准化
3. 实体抽取模块识别关键实体
4. 关系抽取模块识别实体之间的关系
5. 图构建模块把实体和关系组装成图
6. 图存储模块把图写入 Neo4j 或其他图后端
7. 社区发现模块对整张图做聚类
8. 社区摘要模块为每个社区生成摘要
9. 向量索引模块为文本块、实体描述、社区摘要建立向量索引

这一步完成后，系统里就有三层知识表示：

- 原始文本层
- 图结构层
- 社区摘要层

---

## 4.2 在线查询阶段

这一阶段主要负责“用户来问时怎么回答”。

协作顺序通常是：

1. 查询理解模块分析用户问题
2. 系统决定使用图检索、向量检索或混合检索
3. 图检索模块找到相关节点、边、路径或社区
4. 向量检索模块召回相关文本块或社区摘要
5. 上下文重构模块把结果整理成 LLM 可读上下文
6. 回答生成模块生成最终答案
7. 评估与反馈模块记录结果，为后续优化提供依据

---

## 4.3 一个直观示例

用户提问：

“白酒行业上游成本压力会如何影响贵州茅台？”

系统可能这样协作：

1. 查询理解模块识别出关键词：
   - 白酒行业
   - 上游成本
   - 贵州茅台
   - 影响
2. 图检索模块先找到：
   - 贵州茅台属于白酒行业
   - 贵州茅台存在成本相关风险
   - 白酒行业社区中有哪些上游原材料节点
3. 向量检索模块再找：
   - 财报中关于成本、毛利率、原材料的原文描述
   - 行业社区摘要
4. 上下文重构模块把这些信息整理成：
   - 图关系路径
   - 原文证据
   - 社区级总结
5. 回答生成模块输出：
   - 对成本压力的影响分析
   - 影响路径说明
   - 不确定性提示

## 5. 为什么 Graph RAG 比传统 RAG 更复杂

因为它不仅要解决“找相似文本”这个问题，还要解决：

- 图怎么建
- 实体怎么归一
- 关系怎么抽
- 社区怎么划
- 图和文本如何联合检索
- 如何把结构化结果变成 LLM 可消费上下文

所以 Graph RAG 的难点通常不是某一个模型，而是整条链路的工程协同。

## 7. 一句话总结

Graph RAG 不是单一模块，而是一条完整流水线。

它前面负责把文档变成图，后面负责把用户问题变成图检索和文本检索，再把结果整理给 LLM 生成答案。真正强的 Graph RAG，关键不只是用了 Neo4j，而是这些模块能否高质量协作起来。
