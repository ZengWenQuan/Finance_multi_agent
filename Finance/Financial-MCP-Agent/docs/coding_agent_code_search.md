# Coding Agent 如何搜索代码库

## 1. 这类 Agent 在做什么

像 Codex、Claude Code 这类 coding agent，在面对“帮我找一下某个功能代码在哪里”这类任务时，通常不会一开始就把整个代码库做成一个完整知识图谱再分析。

它们更常见的做法是：

**把自然语言需求转成搜索线索，再通过文件搜索、内容搜索、局部阅读、逐步缩小范围的方式定位真正相关代码。**

简单说，就是：

1. 先猜测可能的关键词
2. 用搜索工具召回候选位置
3. 读取局部上下文
4. 判断哪些结果是真相关
5. 再沿着定义、调用链、数据流继续追踪

这本质上很像一个经验丰富的工程师在终端里查代码。

---

## 2. 为什么它们通常不用“先全量建图”

很多人会以为，这类 agent 应该先把整个仓库做成一张代码知识图谱，再统一推理。

但实际工程里，很多时候不会这么做，原因主要有：

### 2.1 代码库经常变化

代码随时会变：

- 新增文件
- 改函数名
- 改调用链
- 改目录结构

如果每次都先做完整重建，成本很高。

### 2.2 大多数搜索问题不需要那么重

很多代码定位问题本质上只是：

- 这个函数在哪定义
- 这个 API 在哪处理
- 这个字段从哪传进来
- 这个报错是哪里抛的

这种问题用：

- 文件树
- 文本搜索
- 局部阅读

通常已经足够快、足够准。

### 2.3 终端工具本身已经很强

像下面这些工具就足够高效：

- `rg` / `grep`
- `find`
- `ls`
- `glob`
- `sed`
- `cat`

所以 coding agent 通常会优先利用现成工具，而不是额外上一个特别重的索引系统。

---

## 3. 它们搜索代码的一般流程

一个比较典型的代码搜索流程，通常可以拆成下面几步：

1. 理解用户意图
2. 生成搜索线索
3. 第一轮粗召回
4. 读取局部上下文
5. 做二次判断
6. 顺着调用链继续查
7. 最终确认目标位置

下面分别说明。

---

## 4. 第一步：理解用户意图

用户通常不会直接给出精确函数名，而是给一个自然语言描述，例如：

- “帮我找匹配功能的函数”
- “看看登录校验逻辑在哪”
- “找一下上传图片的入口”
- “这个风险评分是怎么计算的”

这时候 agent 先要做的不是立刻搜代码，而是先理解：

- 用户说的是哪类功能
- 可能涉及哪一层模块
- 更像入口函数、核心逻辑、还是工具函数

例如：

“匹配功能函数”

它可能会先推断：

- 这可能是业务上的“匹配”
- 可能涉及 compare / filter / rank / score / select
- 不一定函数名真的叫 `match`

所以这一步的本质是：

**把自然语言任务转成可搜索的技术线索。**

---

## 5. 第二步：生成搜索线索

在理解需求后，agent 会为搜索生成一组候选关键词。

还是以“匹配功能函数”为例，可能生成这些线索：

- `match`
- `matcher`
- `matching`
- `compare`
- `filter`
- `score`
- `rank`
- `select`
- 业务对象名
- 输入字段名
- 输出字段名

如果用户的问题里有业务词，它还会把业务词也作为搜索线索。

例如：

- “订单匹配”
- “新闻匹配”
- “股票匹配”

它就可能进一步组合成：

- `order match`
- `match order`
- `news match`
- `stock match`

也就是说，agent 搜索前通常不是只有一个词，而是一组候选线索。

---

## 6. 第三步：第一轮粗召回

接下来 agent 会用搜索工具做第一轮召回。

常见有两类：

### 6.1 搜文件名

查哪些文件或目录名字看起来相关。

例如：

```bash
rg --files | rg "match"
find . -iname "*match*"
```

它想回答的是：

- 有没有模块名直接带 `match`
- 有没有服务文件、工具文件、测试文件名字很像

### 6.2 搜文件内容

查代码内容里有哪些地方出现相关关键词。

例如：

```bash
rg -n "match" .
rg -n "compare|score|rank|filter" .
```

它想回答的是：

- 这个词出现在哪些函数定义里
- 出现在哪些调用点里
- 是否只在注释里出现
- 是否主要出现在测试或文档里

这一步的目标不是直接找到答案，而是先拿到一批候选位置。

---

## 7. 第四步：读取局部上下文

拿到候选结果后，agent 不会把所有文件都完整读一遍。

更常见的是：

- 先读命中行附近几十行
- 看定义、参数、返回值、注释
- 判断这段代码像不像目标逻辑

例如搜索到：

```python
def match_candidates(items, query):
```

它会进一步看：

- 这个函数是在业务模块还是测试模块
- 参数是不是和用户问题一致
- 返回值是不是匹配结果
- 内部是否真的在做筛选/打分/排序

如果只看到：

```python
# TODO improve matching logic
```

那很可能只是注释，不是真正目标。

所以这一步是在做：

**局部上下文验证。**

---

## 8. 第五步：做二次判断

第一轮命中结果里，通常会混进很多噪声。

例如：

- 测试文件
- 注释
- 文档
- 无关的同名字段
- 第三方库代码

所以 agent 会做二次判断，筛掉伪相关结果。

它通常会看这些信号：

- 这是函数定义还是调用点
- 所在目录是不是业务核心目录
- 函数名是否符合语义
- 参数和返回值是否匹配
- 是否被其他核心流程调用
- 附近代码是否出现相关字段、模型、对象

例如用户找“匹配函数”，以下几个候选里：

- `tests/test_matcher.py`
- `docs/matching.md`
- `src/services/order_matcher.py`
- `src/utils/string_match.py`

agent 往往会优先看：

- `src/services/order_matcher.py`

因为它更像业务核心位置。

---

## 9. 第六步：顺着调用链继续查

定位代码时，第一批结果往往不是终点，而只是入口。

比如找到：

```python
def run_match():
    return select_best_candidate(...)
```

这时 agent 会继续搜索：

- `select_best_candidate`

然后再看：

- 这个函数在哪定义
- 谁调用它
- 它内部是不是进一步调用了评分逻辑

这一阶段常见动作包括：

- 从调用点找定义
- 从定义找调用方
- 从 API 路由往下追
- 从数据字段往上追
- 从错误信息反查来源

所以真正的定位过程通常是链式的，而不是一次搜索就结束。

---

## 10. 第七步：不断生成新线索

搜索不是单轮的，而是迭代的。

一个典型过程可能是：

1. 搜 `match`
2. 找到 `order_match_service.py`
3. 读文件后发现核心函数不叫 `match`，而叫 `select_best_candidate`
4. 再搜 `select_best_candidate`
5. 继续发现它内部调用 `calculate_similarity_score`
6. 再搜 `calculate_similarity_score`
7. 最后确认真正核心逻辑在评分函数里

这说明 agent 真正在做的是：

**搜索 -> 阅读 -> 形成新假设 -> 再搜索**

而不是静态一次性检索。

---

## 11. 一个完整例子

假设用户说：

“帮我看看匹配功能函数在哪。”

agent 可能会按下面方式操作。

### 第一步：生成关键词

它会先想到：

- `match`
- `matcher`
- `matching`
- `compare`
- `score`
- `rank`
- `candidate`

### 第二步：搜文件名

例如：

```bash
rg --files | rg "match|matcher|matching"
```

可能找到：

- `src/services/order_matcher.py`
- `src/utils/text_match.py`
- `test/test_matcher.py`

### 第三步：搜内容

例如：

```bash
rg -n "match|matcher|matching|score|rank" src
```

可能找到：

- `def run_match(...)`
- `def select_best_candidate(...)`
- `def calculate_similarity_score(...)`

### 第四步：读局部上下文

读 `order_matcher.py` 后发现：

- `run_match` 只是入口
- 真正筛选逻辑在 `select_best_candidate`
- 打分逻辑在 `calculate_similarity_score`

### 第五步：继续追踪

再搜索：

- `select_best_candidate`
- `calculate_similarity_score`

然后确认：

- 哪个函数是核心逻辑
- 哪个只是包装函数
- 哪个负责 API 接入

### 第六步：输出结论

最后它可能给出这样的判断：

- 入口在 `run_match`
- 核心选择逻辑在 `select_best_candidate`
- 最终匹配分数在 `calculate_similarity_score`

这就是完整定位过程。

---

## 12. 它们常用哪些搜索策略

除了直接搜关键词，这类 agent 还常用这些策略：

### 12.1 按命名约定搜索

例如：

- `service`
- `controller`
- `handler`
- `router`
- `repository`
- `util`

它会结合项目结构猜代码大概在哪一层。

### 12.2 按业务词搜索

例如用户说：

- 订单匹配
- 风险评分
- 财报摘要

它会把业务词和技术词混合搜索。

### 12.3 按数据字段搜索

如果功能名不明显，它会转而搜：

- 输入字段名
- 输出字段名
- 数据模型字段

### 12.4 按报错或日志搜索

用户如果给的是异常信息，它会直接搜：

- 错误文案
- 日志关键字
- 状态码

### 12.5 按测试文件反查

有些代码本体不好找，但测试名字很准。

这时它可能先找到：

- `test_order_matcher.py`

再反向定位生产代码。

---

## 13. 为什么局部阅读很重要

只靠关键词搜索是不够的，因为：

- 同一个词可能到处都有
- 真实核心函数不一定用直白名字命名
- 关键词可能只出现在注释里
- 重要逻辑可能藏在被调用函数里

所以局部阅读的作用是：

- 验证这个命中是不是有效
- 理解代码角色
- 找出下一跳搜索线索

可以说：

**搜索负责召回，阅读负责判别。**

---

## 14. 为什么这种方法通常有效

这种方法有效，是因为代码和普通自然语言不一样，代码本身已经提供了很多强信号：

- 函数名
- 类名
- 文件名
- 目录结构
- 参数名
- 字段名
- import
- 调用链

也就是说，代码天然就是半结构化的。

所以很多时候，只要：

- 关键词选得对
- 搜索范围控制得好
- 局部上下文读得准

就能很快找到核心逻辑。

---

## 15. 它的局限

这种搜索方式虽然实用，但也有局限：

### 15.1 命名很差时会变难

如果代码里都是：

- `do_it`
- `process`
- `handle`
- `run`

这种名字，搜索命中质量会明显变差。

### 15.2 动态分发或反射多时会变难

如果代码 heavily 依赖：

- 动态注册
- 反射
- 字符串路由
- 配置驱动装配

那单纯文本搜索不一定能完整看出真实调用链。

### 15.3 跨仓库调用会受限

如果某段逻辑在别的 repo 或服务里，单仓库搜索只能看到一部分。

### 15.4 真正“理解业务”仍然需要推理

搜到位置不代表已经理解代码，还要靠 agent 去做语义分析。

---

## 16. 一句话总结

像 Codex、Claude Code 这类 coding agent，在搜索代码时，通常不是先做重型全库知识重建，而是先把自然语言需求转成关键词和结构线索，再通过文件搜索、内容搜索、局部阅读、二次筛选和调用链追踪，逐步定位真正相关的代码位置。

---

## 17. 为什么这种方式很依赖 LLM 能力

这种搜索方式表面上看是在“调用命令”，但本质上是一个持续决策过程。

也就是说，agent 不是机械地执行固定命令，而是在不断判断：

- 现在该搜什么
- 搜出来的结果是不是有用
- 下一步该读哪里
- 是否应该继续追调用链

所以这种方法通常比较依赖 LLM 本身的能力。

---

## 17.1 它依赖哪些能力

大致可以分成三类。

### 1. 理解能力

模型要能把用户自然语言问题转成技术搜索线索。

例如用户说：

- “帮我找匹配逻辑”

模型不能只机械地搜 `match`，还要意识到可能相关的词包括：

- `matcher`
- `matching`
- `compare`
- `score`
- `rank`
- `select`
- 业务词本身

如果模型理解能力不足，它第一步就可能猜错关键词。

### 2. 规划能力

模型要知道搜索不是一次完成的，而是一个逐步缩小范围的过程。

它要会决定：

- 先搜文件名还是先搜内容
- 先看入口还是先看核心函数
- 命中太多时该怎么缩小范围
- 该从调用点追定义，还是从定义反查调用方

如果规划能力不足，常见问题就是：

- 乱搜一通
- 重复搜相近关键词
- 不会收敛
- 很快迷失在结果里

### 3. 工具使用能力

模型还要知道不同命令各自适合干什么。

例如：

- `rg` 适合搜关键词
- `rg --files` 适合看文件名候选
- `sed` 适合抓局部上下文
- `head` / `tail` 适合看文件首尾

它不仅要会“调用工具”，还要知道：

- 什么时候该用哪个命令
- 读多少行比较合适
- 什么时候该停下来，不要继续无意义扩展

---

## 17.2 如果模型不够强，会出现什么问题

如果 LLM 不够强，这类 agentic code search 常见会出现下面这些问题：

### 1. 猜关键词不准

它只会搜表面词，不会扩展到更合理的技术词或业务词。

### 2. 搜索范围控制不好

要么搜得太宽：

- 结果太多
- 噪声太大

要么搜得太窄：

- 漏掉真正核心实现

### 3. 不会做二次判断

它可能搜到一个带关键词的地方就误以为找到了答案，分不清：

- 真正定义
- 调用点
- 注释
- 测试代码
- 文档说明

### 4. 不会沿调用链继续追

它找到一个入口函数后，不知道真正核心逻辑可能在下一级函数里。

### 5. 容易做无效重复搜索

例如连续搜：

- `match`
- `matching`
- `matcher`

但没有根据已读上下文生成更强的新线索。

### 6. 容易丢上下文

它可能前面已经看到关键函数了，但后面又忘了，继续在别的地方绕圈。

---

## 17.3 为什么强模型更适合这种方式

强模型的优势不只是“回答更流畅”，而是：

- 更会把自然语言任务转成搜索假设
- 更会从局部代码中提炼新线索
- 更会判断哪些结果是真相关
- 更会控制搜索范围
- 更会维持多步搜索过程中的上下文一致性

所以强模型更适合：

- 多轮搜索
- 动态改关键词
- 顺着调用链追踪
- 面对复杂仓库结构做定位

换句话说：

**越自主的代码搜索方式，越依赖模型本身的推理和决策能力。**

---

## 17.4 弱一些的模型还能不能做

能做，但通常不能完全靠它自主发挥。

也就是说：

- 强模型适合“高自主搜索”
- 中弱模型更适合“半自动搜索”

中弱模型不是完全不能搜代码，而是需要工程层帮它把问题变简单。

---

## 17.5 弱模型常见的补救方法

如果模型不够强，通常可以靠工程手段补。

### 1. 固定搜索流程

不要让模型完全自由发挥，而是要求它必须按固定步骤做：

1. 先找文件名
2. 再找内容命中
3. 再读局部上下文
4. 再判断是否继续追调用链

这样可以减少它乱跳。

### 2. 先做关键词扩展

可以由程序预先给模型一组候选关键词，而不是完全靠它自己猜。

例如“匹配”可以自动扩成：

- `match`
- `matcher`
- `compare`
- `score`
- `rank`

这样能减轻模型第一步的难度。

### 3. 先做代码索引

可以先由程序抽取：

- 文件树
- 函数名
- 类名
- import 关系

然后把这些结构化结果给模型，降低它直接面对整仓库文本的压力。

### 4. 先做符号级搜索

如果能提前拿到：

- 所有函数定义
- 所有类定义
- 所有路由定义

模型只需要在符号表里选目标，再去读文件，就会轻松很多。

### 5. 限制单次读取范围

不要让模型一次读太多无关内容，而是限制：

- 每次只读命中行附近几十行
- 每轮只允许追一两层调用

这样更容易稳定。

### 6. 做更强的流程提示

例如在系统提示里明确要求：

- 先搜关键词
- 再读上下文
- 再给出新搜索词
- 不允许跳过验证阶段

这样可以减少不成熟模型乱下结论。

---

## 17.6 一个更准确的结论

所以更准确地说，不是“只有最强模型才能做代码搜索”，而是：

- 搜索越自主，越依赖模型能力
- 模型越弱，就越要靠工程流程、索引和提示词帮它降难度

也就是说：

**高能力模型适合 agentic search，较弱模型适合 workflow-driven search。**

---

## 18. 补充总结

像 Codex、Claude Code 这类系统之所以能把这套搜索方式用得比较顺，是因为它们不只是“会看代码”，还具备较强的任务理解、步骤规划和工具调用能力。

如果模型本身不够聪明，就不能完全依赖它自由搜索，而应该通过固定流程、预处理索引、关键词扩展和上下文控制，把问题尽量改造成一个更容易处理的搜索任务。
