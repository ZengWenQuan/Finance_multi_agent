# LLM Wiki 详细介绍

## 1. 什么是 LLM Wiki

`LLM Wiki` 可以从两个层面理解：

1. 它是一种知识管理模式
2. 它也是一个具体的开源实现项目

从模式上说，LLM Wiki 的核心思想是：

**不要每次提问时都临时从原始文档里检索碎片，而是让 LLM 持续把原始资料编译成一个持久、结构化、可交叉引用的 wiki。**

从具体实现上说，`llmwiki.app` / `lucasastorian/llmwiki` 是一个开源实现，它把这个模式做成了本地应用、MCP 接口和文件系统工作流。

---

## 2. 这个概念是从哪里来的

公开资料里，`LLM Wiki` 这个思路与 Andrej Karpathy 提出的模式直接相关。

Karpathy 的核心观点是：

- 大多数人对“文档 + LLM”的使用方式是 RAG
- 这种方式每次回答都在重新从原始文档碎片里拼答案
- 知识不会真正沉淀

他提出的替代思路是：

**让 LLM 持续维护一套 interlinked markdown wiki，把知识沉淀成持久资产。**

在这个思路里：

- 人负责挑选资料、提出问题、做判断
- LLM 负责总结、分类、交叉引用、维护结构

也就是：

**人负责思考，LLM 负责知识整理和簿记。**

---

## 3. LLM Wiki 的核心理念

LLM Wiki 的核心不只是“让 LLM 写笔记”，而是把知识管理方式从：

- 临时检索

转变成：

- 持久编译

### 普通 RAG 的思路

普通 RAG 往往是：

1. 你上传一批文档
2. 问题来了再检索相关 chunk
3. LLM 临时拼出答案
4. 这次对话结束后，结果本身不一定沉淀

### LLM Wiki 的思路

LLM Wiki 更像：

1. 你先提供原始资料
2. LLM 持续把这些资料整理进 wiki
3. wiki 内部形成概念页、实体页、摘要页、交叉引用
4. 以后问问题时，LLM 优先基于已经编译好的 wiki 回答
5. 好的回答还能再写回 wiki

所以它不是“每次重新找”，而是“持续建设一个知识资产”。

---

## 4. LLM Wiki 要解决什么问题

LLM Wiki 主要想解决的是下面几类问题：

### 4.1 知识不沉淀

很多 RAG 系统回答完一次问题后：

- 知识没有真正变得更结构化
- 好答案只停留在聊天记录里
- 下一次还得重新检索和重新组织

LLM Wiki 试图把每次 ingest 和每次高质量探索都沉淀下来。

### 4.2 跨文档综合很费劲

一个复杂问题经常涉及：

- 多篇文章
- 多份会议纪要
- 多份研究资料
- 多个概念之间的关系

普通 RAG 要在每次问答时重新拼这些片段。

LLM Wiki 则想提前把这种综合结果变成 wiki 页面。

### 4.3 知识库维护负担太重

传统 wiki 的问题不是没人想用，而是：

- 更新太麻烦
- 交叉引用太麻烦
- 摘要维护太麻烦
- 新资料来了很少有人会系统性重写旧页面

LLM Wiki 的核心卖点之一就是：

**LLM 不怕重复劳动，它可以稳定地做知识维护。**

### 4.4 团队知识容易分散

在企业和研究场景里，知识常常散落在：

- PDF
- 会议纪要
- Slack 讨论
- 飞书/Notion 文档
- 访谈记录
- 表格

LLM Wiki 试图把这些分散信息编译成更统一的结构。

---

## 5. LLM Wiki 和传统 RAG 的区别

最核心的区别是：

### 传统 RAG

- 知识处理主要发生在查询时
- 查询一次，临时检索一次
- 输出更像“即时回答”

### LLM Wiki

- 知识处理更多发生在 ingest 时
- 先编译知识，再查询
- 输出更像“持续维护的知识库页面”

也就是说：

- RAG 更像搜索
- LLM Wiki 更像编纂

---

## 6. LLM Wiki 的三层结构

Karpathy 的模式和 `llmwiki.app` 官方介绍都强调，LLM Wiki 通常有三层结构。

## 6.1 Raw Sources

这一层是原始资料层。

包含：

- 论文
- 文章
- 笔记
- 访谈
- 表格
- 图片
- 转录稿

这一层的规则是：

- 它是 source of truth
- LLM 只读，不改

也就是说，原始资料是不可变的证据层。

---

## 6.2 The Wiki

这一层是 LLM 生成和维护的 wiki 层。

包含：

- 概念页
- 实体页
- 摘要页
- 对比页
- 综合页
- 交叉引用

这一层的规则是：

- 你主要阅读它
- LLM 主要写它和维护它

这也是 LLM Wiki 最核心的产物层。

---

## 6.3 The Schema

这一层是规则层。

本质上是一个指导文档，告诉 LLM：

- wiki 应该怎么组织
- 页面命名怎么做
- ingest 时要更新哪些页面
- query 时怎么回答
- lint 时要检查哪些问题

Karpathy 在模式描述里举的例子包括：

- `CLAUDE.md`
- `AGENTS.md`

这一层很重要，因为没有 schema，LLM 就只是普通聊天模型；有了 schema，它才会成为“有纪律的 wiki 维护者”。

---

## 7. LLM Wiki 的三类核心操作

LLM Wiki 的核心操作通常有三类：

1. Ingest
2. Query
3. Lint

---

## 7.1 Ingest

Ingest 就是把新资料纳入 wiki。

典型过程是：

1. 你把一份新资料放进原始资料目录
2. LLM 读取它
3. 写一个摘要页
4. 更新相关概念页和实体页
5. 更新 index
6. 记录到 log
7. 如果有冲突，标注 contradiction

公开资料里提到，一份新资料可能会影响 10 到 15 个页面。

这说明 LLM Wiki 并不是“存一份摘要”这么简单，而是在做增量知识重组。

---

## 7.2 Query

Query 就是对已经编译好的 wiki 提问。

这里最关键的点是：

**问题不是直接去原始 chunk 里现拼，而是先用已经整理好的 wiki 页面。**

这样做的好处是：

- 结构更稳定
- 回答更像综合知识
- 已有分析可以复用

更进一步，高质量回答还可以反过来写回 wiki，形成新的页面。

这意味着查询过程也能带来知识增量。

---

## 7.3 Lint

Lint 是 LLM Wiki 一个很有特色的部分。

它不是只回答问题，还会主动做知识库健康检查。

比如检查：

- 页面之间是否矛盾
- 哪些信息过时了
- 哪些页面孤立无引用
- 哪些概念被提到但没有独立页面
- 哪些交叉引用缺失
- 哪些地方存在数据空洞

这让 LLM Wiki 更像一个可维护系统，而不是一堆静态笔记。

---

## 8. `llmwiki.app` 这个开源实现是怎么工作的

从开源实现角度看，`lucasastorian/llmwiki` 提供的是一个本地优先的工作流。

它的核心思路是：

1. 你指定一个已有资料文件夹
2. 系统为它建立索引
3. Claude 通过 MCP 接入
4. Claude 读取资料并写 wiki
5. wiki 文件直接落在本地文件系统中

---

## 8.1 它实际做了什么

项目 README 里的描述比较清楚：

1. 你先有一个文件夹，里面放 PDF、笔记、文章、表格等研究资料
2. LLM Wiki 对这个文件夹建立索引，提取文本、切分内容，并建立本地 SQLite 索引
3. Claude 通过 MCP 接入
4. Claude 在 `wiki/` 目录下写页面，并维护交叉引用和脚注引用
5. 随着资料增多，wiki 会持续变厚，而不是每次从零开始

也就是说，这个实现不是“云端托管知识库”，而是一个围绕本地文件夹工作的知识编译系统。

---

## 8.2 它在磁盘上怎么存

这个实现会在你的资料目录旁边增加两部分：

- `wiki/`
- `.llmwiki/`

### `wiki/`

这是你真正的 wiki 页面目录，通常是普通 markdown 文件。

例如：

- `overview.md`
- `log.md`
- `concepts/...`

这一层是可阅读、可编辑、可版本管理的。

### `.llmwiki/`

这是隐藏目录，用来存：

- SQLite 索引
- 缓存
- 处理产物

这一层是派生层，不是最终知识资产层。

官方实现明确强调：

- 文件系统才是 source of truth
- SQLite 只是加速搜索和存储提取结果的派生索引
- 索引可以重建

---

## 8.3 它的本地优先特点

这个实现有一个很重要的特点：

**默认索引、存储和文件写入都发生在本地机器上。**

这意味着：

- 不一定需要云服务
- 对私有研究资料更友好
- 更容易做本地版本管理

这也是它和很多在线 AI 知识库产品的区别。

---

## 9. 它的系统架构

开源实现公开描述的架构比较直观：

- `Next.js` 前端
- `FastAPI` 后端
- `SQLite` 本地索引
- `MCP Server` 连接 Claude Desktop / Claude Code
- `Filesystem` 作为最终 source of truth

也就是说：

- 前端负责界面
- 后端负责 API 和处理逻辑
- SQLite 负责本地搜索索引
- MCP 负责把这些能力暴露给 LLM
- 文件系统负责保存真实知识页面和原始资料

这是一个很典型的“本地知识工作台 + LLM agent”结构。

---

## 10. Claude 在里面扮演什么角色

在这个实现里，Claude 不只是回答问题，而是一个“知识维护 agent”。

项目公开列出的工具能力包括：

- `guide`
- `search`
- `read`
- `write`
- `delete`

这意味着 Claude 可以：

- 浏览 workspace
- 搜索文件和全文
- 读取 PDF、文本和批量文件
- 创建和修改 wiki 页面
- 删除文件

并且每次写入后，索引还会更新。

所以在这个系统里，Claude 更像一个：

- 会读资料
- 会写 wiki
- 会维护结构
- 会更新索引

的知识编辑器。

---

## 11. LLM Wiki 的优势

## 11.1 知识会沉淀

这是它最大的优势。

不像普通聊天问答每次从头来，LLM Wiki 会把知识沉淀为持久页面。

## 11.2 适合长期主题研究

如果你在一个主题上要持续积累：

- 论文
- 文章
- 笔记
- 会议纪要

那 LLM Wiki 非常合适。

## 11.3 交叉引用能力强

它不是简单堆摘要，而是强调：

- 实体页
- 概念页
- 页面之间相互链接

这让知识结构更接近真正 wiki。

## 11.4 适合“知识编纂”而不是临时问答

如果你的目标是构建长期资产，而不是偶尔问一两个问题，那它比纯 RAG 更有吸引力。

## 11.5 适合本地私有资料

开源实现强调本地优先，这对私有研究和内部资料很友好。

---

## 12. LLM Wiki 的局限

## 12.1 不是所有场景都需要

如果你只是做：

- FAQ
- 智能客服
- 简单知识问答

那传统 RAG 往往更直接、更省事。

LLM Wiki 更适合“长期知识建设”，不一定适合每个问答项目。

## 12.2 维护结构依然需要设计

虽然 LLM 会写 wiki，但：

- 页面怎么分层
- 命名规则怎么定
- 哪些信息该独立成页
- 什么叫冲突、什么叫更新

这些仍然需要 schema 设计。

## 12.3 质量依赖 source 和 schema

如果原始资料质量差、范围混乱，或者 schema 设计差，最终 wiki 质量也会差。

## 12.4 不是纯自动真理机

它能做的是：

- 编纂
- 总结
- 交叉引用
- 维护结构

但它依然可能：

- 误解来源
- 过度归纳
- 错误连接

所以人在高质量知识建设里仍然是必要的。

---

## 13. 它适合哪些场景

根据公开描述和模式本身，LLM Wiki 很适合：

- 长期主题研究
- 论文阅读与研究综述
- 团队内部知识沉淀
- 竞争分析
- 尽调
- 课程笔记
- 书籍伴随式阅读
- 企业内部知识编纂

尤其适合：

**知识会持续累积，而且你希望知识不是散落在聊天记录里，而是变成结构化资产。**

---

## 14. 和你前面关心的 RAG / Graph RAG 的关系

LLM Wiki 和传统 RAG、Graph RAG 不是完全同一条线。

### 和传统 RAG 的关系

LLM Wiki 很明确是在批评一种典型问题：

- 每次 query 都重新从 chunk 拼答案
- 知识不积累

所以它更像“RAG 的替代性知识管理思路”。

### 和 Graph RAG 的关系

LLM Wiki 不一定必须做完整 Graph RAG。

它强调的是：

- wiki 页面的结构化
- 页面之间的交叉引用
- 索引、日志、概念页、实体页

某种程度上，它比传统 RAG 更“知识资产导向”，但不一定像标准 Graph RAG 那样强调实体图、路径检索、社区发现。

所以更准确地说：

**LLM Wiki 更像“编译式、持久化、wiki-first 的知识系统”，而不是单纯的检索增强问答系统。**

---

## 15. 一句话总结

LLM Wiki 的核心思想是：让 LLM 不再每次都临时从文档里找答案，而是持续把原始资料编译成一个持久、交叉引用、可维护的 wiki。`llmwiki.app` 则是这个思路的一个本地优先开源实现，它通过文件系统、SQLite、本地前后端和 MCP，把 Claude 变成一个能读取资料、写 wiki、维护结构的知识整理 agent。
